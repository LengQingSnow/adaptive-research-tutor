# 交互式教学协议

## 当前知识点与学习队列

每个点使用稳定 ID，并记录名称、领域、对应任务、前置 ID、重要程度、相关证据、学习状态和未解决问题；完整字段见 [progress-schema.md](progress-schema.md)。默认按依赖顺序，但用户可以自由跳转。新知识插入待学队列，不替换正在学习的点。

| 状态 | 含义及进入条件 |
| --- | --- |
| `pending` | 尚未学习。 |
| `learning` | 已开始讲解，尚无明确理解确认。 |
| `confused` | 用户明确表示没理解；记录具体卡点。 |
| `understood` | 用户明确表示已理解该点；记录确认依据。 |
| `revisit` | 用户要求回顾，或相关实现变化需要重新核对；保留之前的理解确认与原因。 |

课程的暂停与知识点状态分开保存。暂停时保留 active ID、子话题、疑问、依据版本、返回栈和下一步，不把正在学习的点改成完成。

## 反馈决定转移

| 反馈 | 本轮行为 | 状态与位置 |
| --- | --- | --- |
| “没懂”“这部分没看懂”“还是不懂” | 结合上一解释定位可能障碍；换层次或表达，必要时用一个简短澄清问题。 | 当前点转 `confused`，保留/补充疑问，不跨点。 |
| “换一种方式”“举个例子” | 换比喻、具体数值、图示、数据流、时序、推导或实际代码；不只重复原文。 | 留在当前点；明确标注示例与实际事实的边界。 |
| “为什么”“详细讲讲” | 展开因果链、假设、约束或机制。 | 留在当前点。 |
| “懂了” | 记录理解确认，清理本次明确解决的疑问；其他未解决问题仍保留。 | 当前点 `understood`，不擅自开始下一点。 |
| “懂了，继续” | 先记录理解，再选择下一个可学点。 | 旧点 `understood`，新点 `learning`。 |
| 裸“继续” | 无未解决问题时进入下一点；旧点没有明确确认则保留 `learning`。有疑问时继续解释该疑问，简短说明原因。 | 不以“继续”单独推定理解。 |
| “跳过”“先讲 B” | 尊重跳转，标注缺少的前置知识；不强制补课。 | 保留原点状态和疑问，记录返回位置。 |
| 临时问其他概念 | 简单旁支直接回答；需要独立讲解时压入返回栈。 | 不误把对旁支的“懂了”算作原知识点的理解确认；完成旁支可返回原位置。 |
| “同步主任务的最新进度” | 按检查点协议读取可见变化并增量更新队列。 | 当前点、疑问和教学版本仍保留；必要时说明哪些实现内容已经过时。 |
| “暂停教学”“今天到这里” | 在已有权限内保存，或提供会话内恢复摘要。 | 暂停课程；不暂停主开发。 |

连续两次以上“不懂”时也不设置次数上限。区分术语障碍、缺少前置知识、抽象跨度和实现对不上等原因，选择一个更具体的解释。不要重复同一答案后追加必答题；理解检查只能作为可选项。

若队列已无待学项，说明目前队列已覆盖，可以回顾或同步新工作；不为了延长课程凭空添加背景概念。

## 单点讲解

以下是可选的展开维度，不是每次都要照搬的六个标题：

- **What**：定义、目标、实际用途。
- **Why**：问题、动机、约束。
- **How**：机制、算法、推导、架构、数据流或状态变化。
- **Implementation**：当前工作中读到的代码、模块、公式、配置、数据或实验。
- **Trade-offs**：合理替代方法与性能、复杂度、可靠性、成本的取舍；设计动机无记录时标为推断。
- **Verification**：怎样验证；明确已执行结果、理论预期和还未运行的检查。

从关键因果关系开始，给足理解当前点的内容；复杂推导按用户反馈分段。图示只有在改善解释时使用。没有项目证据时仍可讲通用原理，但不得伪造“当前代码就是这样”。

例如：用户卡在平均为何降噪，可用“假设真实读数为 20，测得 19、21、20，平均为 20”解释误差抵消，并说明这只是教学数值；平均不消除固定偏差，随机噪声下降依赖噪声关系等条件。此后留在该点，不要求用户答题才继续。

## 知识背景

发布版本不内置任何特定学习者的知识背景。用户可自愿说明自己已掌握的知识、尚不熟悉的部分和期望的讲解深度；这些信息可以留空，不作为开始教学的前置条件。

只保留当前用户提供、与讲解相关的声明和本次会话的理解反馈；个人背景只在获准的会话或项目学习记录中维护，不写入公共 Skill。给推测的背景标注低置信度，不把它当作用户事实。用户可以随时要求更基础或更深入；调整当前讲法而不重启课程或强制测评。
